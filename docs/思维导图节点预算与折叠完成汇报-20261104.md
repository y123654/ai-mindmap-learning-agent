## 3. 实现要点

1. **接入点**：`SyncEngine.prepare()` 的 `capDecision.active()` 分支内，`filterMergedOperations` 之后、`validate` 之前。不触发三级裁剪的文档（预计 ≤100）**完全不进预算器**，所以"≤200 的文档逐字节不变"。
2. **优先级**：标题（`#heading(`）永不折 → 先折一级列表项（`#bullet(`）→ 仍超限再折 AI 段落节点（`ai_enhanced`）。
3. **只折叶子**：任何 add 的 `parentId` 都不折，宁可少折也不产生孤儿。
4. **名额分配**：按父组大小用最大余数法，名额够时每组先保 1 个；硬断言 `sum(keep) == keepTotal`、`0 <= keep_i <= size_i`，余数相同按父组出现顺序（确定性）。
5. **折叠文本**：`[节点预算折叠] 已折叠 N 项：标签1；标签2；…` 追加到父节点 summary；父节点是本批 add 就直接改，是已有图节点就生成一条合并的 `update_node`；父节点受手动保护（`manualLocked` / `manuallyEdited` / `source_type=manual`）或不在图里，则写"最后一个保留子节点"。
6. **幂等**：重写前逐行删掉带 `[节点预算折叠]` 的旧段，重复同步不会堆叠。
7. **上限**：`min(summary-max-chars, MAX_SUMMARY_LENGTH=500)`，截断加 `…` 并计数 + WARN。
8. **结构超限**：标题本身超过上限时抛 `MINDMAP_STRUCTURE_TOO_LARGE`，文案是"…标题无法折叠，请拆分文档后再同步"，**不提示重试**。

## 4. 偏离方案的地方（共 6 处，全部有理由）

| # | 偏离 | 理由 | 谁定的 |
|---|---|---|---|
| 1 | `fixed >= cap` → **`fixed > cap`**（方案 §4.2.3 是 `>=`） | `fixed == cap` 时把所有候选折掉正好等于上限，按 `>=` 会白白失败，违背 §2.1 目标 1。已补边界用例 `fixedEqualsCap_...` | 我（组长）拍板 |
| 2 | 错误文案"请拆分文档后**重试**" → "**再同步**" | 方案 §4.4 示例含"重试"，但 §7 验收要求"不含'重试'误导"，按 §7 执行 | 我拍板 |
| 3 | 引擎侧日志用 `log.info`，不重复打"折叠生效" | 预算器内部已有一行 WARN，两行完全一样是噪音 | 我拍板 |
| 4 | `canWriteParent` 额外把 `source_type=manual` 判为不可写（方案只写 manualLocked / manuallyEdited） | 校验器 `validateUpdate` 同样拒绝 manual 节点；不这样会生成一条注定让整单失败的 update | 子 agent 报备，我复核认可 |
| 5 | 旧用例 `bulletsCannotSave_fallsBackToAiParagraphPass` 的输入 30→35 个 AI 段落、`foldedAdds` 断言 5→10 | 它的前提正是 `fixed=40 >= cap=40`，即第 1 条要修掉的边界；覆盖意图（第一轮救不回来→第二轮折 AI）与另外三条断言原样保留，代码里有注释说明 | 子 agent 报备，我判定**不是凑绿** |
| 6 | 测试桩 `stubAddNodeForEachAddedParagraph` 泛化为"只回本批段落" | 36 个段落会被拆成多批，原桩每批都回 36 个，`AiOperationConverter` 直接拒收；新桩才符合真实 AI 行为，单段落旧用法行为不变 | 子 agent 报备，我复核认可 |

另外记录：方案自身有两处小矛盾——§1.1 说 180 个列表项、§6.1 用例 2 写 179；§4.4 文案与 §7 口径冲突。前者不影响验收（总数 248、上限 200 一致），后者按 §7 执行。

## 8. 未做 / 风险（照实列）

1. **手工全栈验收只完成了一半**：接口层跑通了（见第 7 节），但日志归档与端到端回滚没拿到（双实例抢 MQ）。
2. **真机回滚没跑**（改环境变量 → 重启 → 复现 248>200）：只到"绑定层 + 逻辑层"证据，端到端回滚留给下次全栈验证。
3. **summary 500 截断只有单测**：真实"一个父节点下几十个列表项"的场景没跑过，截断后的可读性未评估。
4. **折叠对用户是"看不见"的**：文本只进 summary（前端悬停可见），节点框内不显示。用户可能感知为"内容变少了"——方案明确"不改前端"，本轮遵守。
5. **深文档仍可能超限**：只折叶子；嵌套列表（有子节点）不折，标题过多时仍抛 `MINDMAP_STRUCTURE_TOO_LARGE`，属于预期行为。
6. **`max-new-nodes` 现在可配置**：若有人设成 >200，等于绕过 §9.4 硬上限。方案允许（默认仍是 200），但运维要知道这个口子。
7. **幂等依赖标记行**：如果用户手工编辑 summary 并删掉 `[节点预算折叠]` 那行，下次同步会认为没有旧段而重新追加（边角，未验证）。
