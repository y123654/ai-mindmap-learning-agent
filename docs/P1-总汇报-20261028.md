## 一、一句话结论

**P1 把「单轮工具调用」升级成了「按意图路由 + 受控编排 + 证据边界 + 预算约束」的 Agent，测试基线从 727 涨到 1126 全绿，Flyway 零新迁移。**
但必须同时说清：**除 P0 那组（改造前的）数字外，P1 至今没有任何真实评测数字**；两次专项测量（E2/E2b）的结论多数是"测不出差异"和"某个手段没有收益"。

## 三、两次测量真正给出的结论（这部分可以直接对外讲）

### 3.1 "多查询/RRF 没有测出召回收益"
- 干净夹具（E2）：基线 recall@5 已经 **1.0000**（严格口径 0.8030），19 组配置 18 组满分 → **夹具封顶，测不出**；
- 干扰夹具（E2b）：塞 40 条同领域干扰把候选池从 5 拉到 45，**recall@5 仍 +0.0pp**；
- 三个手段（多查询 / cap 8 / 每篇 2 chunk）**都没有任何抗噪差异（0.0pp）**。

### 3.2 "LLM 改写只买到延迟"
- recall/MRR **+0.0pp**，P50 **+780~863ms**（960~1043ms vs 176~198ms）→ 已按数据把 **LLM 改写默认关**，保留零成本的规则改写 + RRF。

### 3.3 "噪声伤的是排序，不是召回"
- 干扰下 MRR **-4.5pp**、recall@1 **-9.1pp**（15 条用例第一名被抢）、**每次返回 4.70 条证据里约 2.30 条是噪声**；
- 但 gold 仍在 top5 内 → recall@5 没掉。
- 推论：**"抬阈值去噪"这条路被夹住**——`minScore=0.45` 实测会丢 gold（-2.0pp），`0.35` 又拦不住同领域噪声。

### 3.4 工程收口是可量化的
- 补检最坏耗时 **150s → 75s**（原来第二轮会新开一个 75s 预算）；
- 三条路径最坏耗时写清：**旧路径 75s / 补检 75s / 计划常态 75s（设计软上限 80s）**，且 **80s 不是 P95 预期**。

### 3.5 真实数据上的误伤检查（45 条历史回答，零成本）
- E3b 回答侧：**leaked = 0 / 45**（真实回答上零误伤）；
- D2 规则触发面：**35/45（77.8%）**有"关键结论句无引用"——但这是**触发面不是误报率**（证据表为空 → 实际走整体提示，逐句补充说明触发 0 条）。

## 五、开关矩阵（写简历/讲项目时必须带这个）

| 能力 | 配置项 | 默认 | 备注 |
|---|---|---|---|
| 意图路由 / 补检 / 计划 / 引用自检 | `app.agent.runtime.enabled` | **false** | 关着 = 走 P0 旧编排 |
| 工具预算软降级 | `app.agent.tool-budget-soft` | **true** | 改默认行为：第 4 次不再中止 |
| 单工具超时 | `app.agent.tool-timeout-seconds` | 10 | 超时 retryable |
| 多查询 + RRF | `app.agent.retrieval.multi-query-enabled` | **true** | 默认走规则改写 |
| **LLM 查询改写** | `app.agent.retrieval.rewrite-llm-enabled` | **false** | E2c 按数据关掉 |
| 检索条数 / 每篇 chunk | `max-results` / `max-chunks-per-document` | 5 / 2 | 可校准 |
| 注入防护 | `app.agent.security.evidence-guard-enabled` | **true** | 关掉 = 旧输出逐字节 |
| run 总预算 | `app.agent.timeout-seconds` | 75 | 全阶段共享 |

**三个"不开开关也生效"的批次**：D1（工具软降级）、E1（多查询）、E3b（证据包装）。想回到纯 P0 行为，需要同时关掉这三处 + `runtime.enabled=false`。

## 六、如果以后要跑 P1-F（建议的跑法）

1. **先跑一次 `runtime.enabled=true`**（≈¥10~25）：这才是"P1 全开"的数字。用 `false` 跑等于跑旧编排，钱基本白花。
2. 若预算允许，**再跑一次 `runtime.enabled=false`**（其余开关完全相同）→ 两次之差才是"P1 编排能力"的净增量（合计 ≈¥20~50）。
3. 报告名带 `runtime-on` / `runtime-off`；把 `configSnapshot` 13 键作为前置条件；并注明 P0 与现在的口径断层（evidence 包装 + 多查询）。
4. 已知无法统计的：**软降级命中数**（不落 `agent_tool_calls`）→ 不能把"硬中止=0"当"没触到上限"。

## 七、面对面试/简历怎么说（诚实版）

**可以说：**
- "按意图路由的单 Agent 编排：简单问题单轮、知识问题强制检索并标来源、多跳问题拆子问题并发检索后合成"；
- "引用自检 + 逐句补充说明，且**流式不撤回**（这是流式与校验的取舍）"；
- "工具预算软降级 + run 级统一预算，把最坏耗时从 150s 收到 75s"；
- "用专项测量否掉了自己的假设：多查询/RRF 在现有夹具上无召回收益，LLM 改写 +780ms 零收益 → 关掉它"；
- "45 条真实回答上做离线误伤抽检，回答侧零误伤"。

**不能说（会被追问穿）：**
- "F1 提升到 0.85+" / "引用覆盖率达到 85%"——**没测过，P0 的两个门槛都还没达**；
- "检索变好了"——两次测量都是 +0.0pp，而且是**夹具封顶**；
- "模型不会执行提示注入"——只验证了包装/转义/标记等机制；
- "完整 Plan-and-Execute"——是缩减版（不做充分性判定/改写重查/补充轮）。
