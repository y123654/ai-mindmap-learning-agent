# 思维导图节点预算与折叠实施方案 v1.0

> 对象：`mindmap-backend` 的同步链路（Markdown → 思维导图）
> 触发问题：`单次同步新增节点 248 个，超过上限 200 个（§9.4）`
> 样本：`samples/复杂Markdown示例2-Agent智能体知识-原文.md`（5,287 字符 / 317 行）
> 性质：**缺陷修复**（不是新功能）。宽文档不应该因为"节点多"整单失败，而应该在预算内生成，并把折叠内容保留下来。
> 实施前置：先读 `AGENTS.md`、`docs/项目总验收记录-20261025.md` 第九节、`docs/思维导图节点超限诊断-20261103.md`。
> 开工纪律：**本轮只做本文范围，不顺手改 AI 提示词、不改分批、不改表结构、不改前端。**

---

## 0. 一句话方案

在 `SyncEngine.prepare()` 的"三级裁剪之后、校验之前"加一个**节点预算器**：
本次新增超过 200 时，优先保留标题结构，再按父节点比例折叠**同级列表项**——被折叠项的文本写进父节点（或最后一个保留子节点）的 `summary`，保证最终 `add_node ≤ 200`，**不再整单失败**。

---

## 1. 背景与根因（必须理解，否则会改错地方）

### 1.1 248 是怎么来的

样本文件结构：

| 结构 | 数量 |
|---|---:|
| H1（根） | 1 |
| H2 | 8 |
| H3 | 23 |
| 一级列表项 | 180 |
| 普通段落（AI 各生成 1 个节点） | 36 |
| **合计** | **248** |

### 1.2 为什么现有"三级裁剪"没生效

`MindMapDepthCap` 是**按深度**裁的：

- 标题只保留 H1–H3（样本没有 H4，32 个全保留）；
- 列表只保留**一级缩进**（样本 180 项全是一级缩进，全保留）；
- 段落只保留挂载深度 ≤3（36 个全保留）。

裁剪确实触发了（248 > 100），但**一个节点都没裁掉**，最后撞 `MindMapOperationValidator.MAX_NEW_NODES_HARD = 200`。

**这份文档是"宽"（同级并列项多），不是"深"；深度裁剪对它无效。**

### 1.3 为什么不能靠"重试"或"只加缩进"

- 重试是确定性的：同样输入每次都是 248，重试只会重复失败；
- 只把子项缩进 2 格：解析器能建层级，但三级裁剪只允许一级缩进，二级项会被整批丢弃，用户看到"内容少一半"。

### 1.4 为什么不用"把上限调到 300"

- 只是把悬崖从 200 移到 300，下一份 500 节点的文档照样失败；
- 248 个节点在画布上已经偏密，不解决"宽文档应该给出可读结构"的问题；
- 上限 200 是 v1.1 §9.4 的产品约束，不应为了一个样本改基准。

**所以要做的是"预算 + 折叠"，不是"提高上限"。**

## 2. 目标与非目标

### 2.1 目标

1. 任意宽文档（标题不多、列表很多）都能在 `maxNewNodes`（默认 200）内生成，**不再因 `VALIDATION_FAILED` 整单失败**。
2. 折叠不丢文本：被折叠项的 `label` 写进父节点/保留子节点的 `summary`，前端悬停可见。
3. 结构优先：标题（H1–H3）永远保留；先折列表项，列表不够再折 AI 段落节点。
4. 小于等于上限的文档**行为逐字节不变**（现有测试锁死）。
5. 错误信息可执行：确实无法折叠时，明确告诉用户"结构本身超限，请拆分"，不再提示"重试"。
6. 默认开启、可回滚（`app.mindmap.fold-enabled=false` 恢复旧行为）。

### 2.2 非目标（明确不做）

- 不改 `MAX_NEW_NODES=100` / `MAX_NEW_NODES_HARD=200` 的默认值；
- 不改 AI 提示词、分批策略、`maxPromptChars`；
- 不改数据库表结构（**不需要 Flyway**）；
- 不改 REST DTO / JSON 契约；
- 不做"一份文档生成多张导图"（那是另一个产品方案）；
- 不做 LLM 语义精简（后续可选）；
- 不改前端（摘要已由 `MindMapNodeView` 的 `title` 与 `.mindmap-node-summary` 渲染）。

### 2.3 硬约束

- 测试只增不减；全量基线当前 **1126 全绿 / Skipped 4**。
- 所有失败路径、截断、结构超限都要有日志；不打印节点正文（只打计数/ID）。
- 新逻辑默认开启属于"改默认行为"，必须在汇报里单独标注并给回滚开关。
- 改动前先读文件；改完贴真实 `mvn test` 与 `npm run build` 结果。

## 3. 方案总览

```
SyncEngine.prepare()
  PARSING → DIFFING → 规则操作
  → MindMapDepthCap.decide()          （既有：>100 触发深度裁剪）
  → filterRuleOperations / filterAiContext
  → AI 调用（既有）
  → filterMergedOperations            （既有：按深度/结构过滤）
  → 【新增】MindMapNodeBudget.apply()  ← 本文核心
  → MindMapOperationValidator.validate(..., maxNewNodes)
  → GraphPreviewBuilder.preview()
```

### 3.1 预算优先级

1. **标题节点**（`sourceAnchor` 含 `#heading(`）：不可折叠，定义结构；
2. **列表节点**（`sourceType="markdown"` 且 `sourceAnchor` 含 `#bullet(`）：第一优先级折叠；
3. **AI 段落节点**（`sourceType="ai_enhanced"`）：第二优先级折叠；
4. 如果"标题节点 + 根"本身就超过上限：无法折叠，抛 `MINDMAP_STRUCTURE_TOO_LARGE`，提示拆分文档。

### 3.2 折叠方式（v1 不新增节点）

- 每个父节点下，按文档顺序保留前 K 个可折叠子节点；
- 被折叠的项，把 `label` 拼成一段文本，追加到**父节点**的 `summary`：
  `已折叠 N 项：标签1；标签2；…`
- 父节点不在本批 `add_node` 里（增量同步的已有节点）时，生成一条 `update_node` 更新其 summary；
- 父节点受手动保护（`manualLocked` / `manuallyEdited`）时，改为追加到"最后一个保留子节点"的 summary，避免覆盖用户内容；
- 每个 summary 上限 500 字符（与 `MindMapOperationValidator.MAX_SUMMARY_LENGTH` 一致）；放不下时截断并 `WARN`（只打 parentId / foldedCount / 原长度）。

> 不新增"其余 N 项"节点，是为了保证"折叠一定不增加节点数"，算法可证明收敛。
> 如果后续要做可见的折叠节点，另立方案，不在本轮。

### 4.2 新增预算器

`mindmap-backend/src/main/java/com/example/aimindmap/mindmap/MindMapNodeBudget.java`

```java
@Component
public class MindMapNodeBudget {

    public BudgetResult apply(List<ValidatedOperation> operations,
                              MindMapGraph currentGraph,
                              MindMapProperties properties);

    public record BudgetResult(
            List<ValidatedOperation> operations,
            int keptAdds,
            int foldedAdds,
            int foldedParents,
            int truncatedSummaries) { }
}
```

#### 4.2.1 识别可折叠节点

```java
private static boolean isAdd(ValidatedOperation op) {
    return op != null && "add_node".equals(op.type()) && op.node() != null;
}

private static boolean isHeading(MindMapNode n) {
    return "markdown".equals(n.getSourceType())
            && n.getSourceAnchor() != null
            && n.getSourceAnchor().contains("#heading(");
}

private static boolean isBullet(MindMapNode n) {
    return "markdown".equals(n.getSourceType())
            && n.getSourceAnchor() != null
            && n.getSourceAnchor().contains("#bullet(");
}

private static boolean isAiParagraph(MindMapNode n) {
    return "ai_enhanced".equals(n.getSourceType());
}
```

**只折叠叶子节点**：候选节点不能是任何 add 操作的 `parentId`（避免产生孤儿）。
在样本里 180 个列表项都是叶子；如果某个列表项有嵌套子项，本轮跳过它（宁可少折，也不产生孤儿）。

#### 4.2.2 主流程（伪代码）

```java
List<ValidatedOperation> result = new ArrayList<>(operations);
int cap = properties.getMaxNewNodes();
int addCount = countAdds(result);
if (!properties.isFoldEnabled() || addCount <= cap) {
    return new BudgetResult(result, addCount, 0, 0, 0);
}

int foldedAdds = 0;
int foldedParents = 0;
int truncated = 0;

// 第一轮：列表项
FoldPass pass1 = fold(result, currentGraph, cap, CandidateType.BULLET,
        properties.getSummaryMaxChars());
result = pass1.operations();
foldedAdds += pass1.foldedAdds();
foldedParents += pass1.foldedParents();
truncated += pass1.truncatedSummaries();

// 第二轮：列表折完仍超限，再折 AI 段落节点
if (countAdds(result) > cap) {
    FoldPass pass2 = fold(result, currentGraph, cap, CandidateType.AI_PARAGRAPH,
            properties.getSummaryMaxChars());
    result = pass2.operations();
    foldedAdds += pass2.foldedAdds();
    foldedParents += pass2.foldedParents();
    truncated += pass2.truncatedSummaries();
}

// 仍然超限：结构本身太大（标题太多），无法靠折叠解决
if (countAdds(result) > cap) {
    throw ApiException.badRequest("MINDMAP_STRUCTURE_TOO_LARGE",
            "文档结构本身超过单次上限：新增节点 " + countAdds(result)
            + " 个（上限 " + cap + " 个），标题/不可折叠节点过多，无法靠折叠解决，请拆分文档后同步");
}

return new BudgetResult(result, countAdds(result), foldedAdds, foldedParents, truncated);
```

#### 4.2.3 单个 pass 的分配算法

```java
FoldPass fold(List<ValidatedOperation> ops,
              MindMapGraph currentGraph,
              int cap,
              CandidateType type,
              int summaryMaxChars) {

    int addCount = countAdds(ops);
    int need = addCount - cap;
    if (need <= 0) return FoldPass.noop(ops);

    // 1. 收集候选：叶子 + 指定类型
    Map<String, List<ValidatedOperation>> groups = new LinkedHashMap<>();
    for (op : ops) {
        if (!isAdd(op) || !isCandidate(op.node(), type)) continue;
        if (hasChildAdd(ops, op.nodeId())) continue;       // 非叶子，跳过
        groups.computeIfAbsent(op.parentId(), k -> new ArrayList<>()).add(op);
    }

    int foldable = sum(groups, List::size);
    if (foldable == 0) return FoldPass.noop(ops);

    int fixed = addCount - foldable;                       // 标题 + 不可折叠节点
    if (fixed >= cap) {
        // 预算本身就是结构吃满，交给上层抛 MINDMAP_STRUCTURE_TOO_LARGE
        return FoldPass.noop(ops);
    }

    int keepTotal = Math.min(foldable, cap - fixed);       // 可保留的候选数
    int foldTotal = foldable - keepTotal;

    // 2. 分配 keepTotal 到各父组
    Map<String, Integer> keepByParent = allocate(groups, keepTotal);

    // 3. 应用：每组保留前 K 个，折叠其余
    Set<String> removedIds = new HashSet<>();
    int groupsFolded = 0;
    int truncatedCount = 0;

    for (var entry : groups.entrySet()) {
        String parentId = entry.getKey();
        List<ValidatedOperation> candidates = entry.getValue();
        int keep = keepByParent.getOrDefault(parentId, 0);

        // keep=0 时没有"保留子节点"可承接文本，优先写父节点；
        // 若父节点受手动保护/不可写，则把 keep 提升为 1，并从别的组借 1 个名额（保证总数不变）。
        if (keep == 0 && !canWriteParent(ops, currentGraph, parentId)) {
            keep = 1;
            rebalanceOneKeep(keepByParent, groups, parentId);
        }

        List<ValidatedOperation> folded = candidates.subList(keep, candidates.size());
        if (folded.isEmpty()) continue;

        groupsFolded++;
        String text = foldText(folded);                    // "已折叠 N 项：a；b；…"
        if (appendSummary(ops, currentGraph, parentId,
                keep > 0 ? candidates.get(keep - 1) : null,
                text, summaryMaxChars)) {
            truncatedCount++;
        }
        for (op : folded) removedIds.add(op.nodeId());
    }

    // 4. 过滤：删掉被折叠的 add、引用被删节点的 update/propose_remove
    //    修复 afterNodeId 指向被删节点的情况（本轮是后缀折叠，理论上不需要，但要做兜底）
    List<ValidatedOperation> output = filterAndRepair(ops, removedIds);

    return new FoldPass(output, foldTotal, groupsFolded, truncatedCount);
}
```

辅助定义：

- `canWriteParent(...)`：父节点是本批 `add_node`，或存在于 `currentGraph` 且不是 `manualLocked` / `manuallyEdited`；
- `rebalanceOneKeep(...)`：从另一个 `keep > 1` 的组减 1（优先选 keep 最大的组，平局按组顺序），
  把名额让给当前组；必须断言 `sum(keep)` 不变；
- `FoldPass`：`record FoldPass(List<ValidatedOperation> operations, int foldedAdds, int foldedParents, int truncatedSummaries)`；
- `foldText` / `appendSummary` 见 §4.2.5。

#### 4.2.4 分配 `keepTotal`（必须确定、可测）

按父组大小比例分配，并尽量保证每组至少留 1 个：

1. 如果 `keepTotal >= groups.size()`：每组先分 1 个；
2. 剩余 `left = keepTotal - groups.size()`，按 `group.size()` 比例分配；
3. 用"最大余数法"处理取整误差（余数相同按父组出现顺序）；
4. 任何一组 `keep <= group.size()`；
5. 最终 `sum(keep) == keepTotal`。

伪代码：

```java
int[] keep = new int[groups.size()];
int base = (keepTotal >= groups.size()) ? 1 : 0;   // 名额够就每组先保 1 个
int assigned = 0;
for (i) { keep[i] = Math.min(base, size_i); assigned += keep[i]; }
int left = keepTotal - assigned;

// 按"应得份额的小数部分"从大到小补 1，平局按组出现顺序，保证确定性
while (left > 0) {
    选 fractional_i 最大且 keep_i < size_i 的组 +1；
    left--; assigned++;
}
```

> 简化实现也可以：`keep_i = floor(keepTotal * size_i / foldable)`，再按余数补齐。
> 测试必须断言 `sum(keep) == keepTotal`、`0 <= keep_i <= size_i`，不要只测"大概"。
>
> 边界：当 `keepTotal < groups.size()` 时，必然有组 `keep=0`。若该组父节点可写，整组文本进父节点 summary；
> 若父节点不可写（已有节点且手动锁定），先从 `keep>1` 的组借 1 个名额；借不到就抛
> `MINDMAP_STRUCTURE_TOO_LARGE`（宁可明确失败，也不静默丢文本）。

**本样本的算例**（实现后应能复现）：

```
fixed   = 标题 32 + AI 段落 36 = 68
foldable= 列表 180
cap     = 200
keepTotal = min(180, 200 - 68) = 132
foldTotal = 180 - 132 = 48
groups    = 14 个"有列表子节点"的父节点（12 个 H3 + 2 个直接挂列表的 H2）
每组先保 1 个（14），剩余 118 按比例分配 → 合计 132
折叠 48 项，文本进入各自父节点 summary
最终 addCount = 68 + 132 = 200
```

#### 4.2.5 折叠文本与 summary 写入

```java
private static String foldText(List<ValidatedOperation> folded) {
    StringBuilder sb = new StringBuilder("已折叠 ").append(folded.size()).append(" 项：");
    for (int i = 0; i < folded.size(); i++) {
        if (i > 0) sb.append("；");
        sb.append(oneLine(folded.get(i).node().getLabel()));
    }
    return sb.toString();
}
```

写入规则：

- **父节点是本批 add**：直接改 `parentOp.node().summary`；
- **父节点是已有图节点**：
  - `GraphIndex.of(currentGraph).findById(parentId)`；
  - 若父节点 `manualLocked` 或 `manuallyEdited`：改写到"最后一个保留子节点"的 summary（那个节点是本批新增的，安全）；
  - 否则创建/合并一条 `update_node`（同一 parentId 只一条），`node` 用 `deepCopy()`，summary 追加；
- **父节点既不在本批也不在 currentGraph**：改写到最后一个保留子节点；若 `keep == 0`，把 `keep` 调整为 1（保留一个承接文本），并在日志里记 `fallbackKeep`；
- 追加格式：
  - 原 summary 为空：`text`；
  - 非空：`原 summary + "\n" + text`；
- 长度：`min(properties.getSummaryMaxChars(), MindMapOperationValidator.MAX_SUMMARY_LENGTH)`；
  - 若剩余空间不足，截断 `text` 并加 `…`，`truncatedSummaries++`，`WARN` 日志（parentId、folded 数、原长度、上限）；
- **幂等**：如果原 summary 已包含标记 `[节点预算折叠]`，先删掉旧段再追加，避免多次同步重复堆叠。
  建议格式：`\n[节点预算折叠] 已折叠 N 项：…`。

#### 4.2.6 `afterNodeId` 与引用清理

- 被折叠节点从 `operations` 删除；
- 任何 `update_node` / `propose_remove_source_node` 的 `nodeId` 落在 `removedIds`：一并删除（这些节点不会再存在）；
- 任何保留的 add 的 `afterNodeId` 落在 `removedIds`：在同父组内向前找最近保留节点；找不到置 `null`；
- 任何保留的 add 的 `parentId` 落在 `removedIds`：说明折了非叶子，属于实现错误——**不要静默**，抛 `IllegalStateException` 并由上层转 `MINDMAP_STRUCTURE_TOO_LARGE`（测试要覆盖）。

### 4.4 校验器文案

`MindMapOperationValidator` 的 `VALIDATION_FAILED` 消息保留（预算后不应再因宽度触发）。
新增的 `MINDMAP_STRUCTURE_TOO_LARGE` 消息必须包含：

```
文档结构本身超过单次上限：标题 X 个 + 新增节点 Y 个，上限 200 个。
```

## 9. 风险与回滚

| 风险 | 影响 | 对策 |
|---|---|---|
| 折叠后 summary 太长 | 节点悬停信息冗长 | 上限 500 + 截断日志；v1 不显示在节点框内 |
| 父节点受手动保护 | 不能覆盖用户内容 | 改写到最后一个保留子节点；测试 13 |
| 增量同步重复折叠 | summary 堆叠 | `[节点预算折叠]` 标记 + 先删旧段；测试 14 |
| 嵌套列表被误折 | 产生孤儿、校验失败 | 只折叶子；测试 15 |
| 标题本身超 200 | 无法折叠 | 明确报错 + 提示拆分，不静默 |
| 默认开启改变行为 | 老用户预期变化 | 汇报单独声明；`fold-enabled=false` 回滚 |
| 折叠被误认为"丢数据" | 用户投诉 | summary 保留文本；汇报写明"折叠不是删除" |

**回滚**：`app.mindmap.fold-enabled=false`（或 `MINDMAP_FOLD_ENABLED=false`）重启，恢复旧行为；无 DB 迁移，无需数据回滚。
